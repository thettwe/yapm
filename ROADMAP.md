# yapm — Roadmap

Scope decisions from the v1 scoping session (2026-07-23). Each item becomes an OpenSpec change (`openspec/changes/`) when its turn comes — proposals are written just-in-time, not upfront.

## V1 scope (locked)

**Shape**: one workspace per instance → teams → issues. Roles: admin / member / viewer (viewer free and unlimited).
**Tracking**: issues (status, priority, labels, assignee, TipTap description, comments) · cycles with auto-rollover · triage inbox · lightweight projects (name, lead, target date, membership, computed progress).
**Surfaces**: keyboard-first list · board · roadmap (timeline of projects) · command palette · search/filtering.
**Wedge proof**: GitHub App — branch/PR ↔ issue linking, PR state drives issue status, PR + checks visible on the issue.

**Opinionated defaults (not asked, decided per philosophy):** fixed status categories (Backlog / Todo / In Progress / In Review / Done / Canceled); estimates deferred; sub-issues deferred; notifications = in-app inbox + email for mentions/assignments.

**Where v1 actually stands.** The **PM core** (changes 1–7 plus `design-system`) is complete: workspace/auth, design system, issues, board, cycles, triage, and projects with a roadmap. With `connectors` (8) the delivery-truth wedge is live — GitHub PR/CI/deploy state feeds the issue-row reality strip and divergence flag. With `ai` (9) the BYO-key AI foundation and its first flagship, the team-internal cycle digest, are in. With `retro-board` (10) the team has the surface where it decides what to change, shipping with no AI in it at all. With `notifications` (11) the work graph can finally reach a person: a self-scoped inbox, and the provider-neutral mailer the rest of the product's outbound email now goes through. With `mentions` (12) a person can be reached *by name*, and the issue they were named on keeps reaching them until they say stop.

**V1 is not complete.** Two things the locked scope above names had never been built, and saying "V1 PM core complete" obscured them. One is now closed:

- **Notifications** — "opinionated defaults" commits to "in-app inbox + email for mentions/assignments". Closed by changes 11 and 12: the in-app inbox, the assignment and comment triggers, and batched email ship in 11 (and `SMTP_URL` finally has a consumer); the *mentions* half of that sentence ships in 12, which turned out to be more than a notification kind — auto-subscribe made it a new synced entity with its own migration.
- **Search** — "Surfaces" commits to "search/filtering". Filtering shipped in `issue-core`; search did not. `grep -rn "ilike|tsvector|to_tsquery"` over `apps` and `packages` returns nothing.

Changes 11–13 close both. They are scoped — sequence, overlaps, constraint checks, falsifiable checks, and the decisions that need a human — in [`openspec/SCOPE-v1-gaps.md`](openspec/SCOPE-v1-gaps.md), which is the mission input for those three build flows. After them, what remains is AI *features* on the change-9 foundation (the governed PM-facing digest, the **AI-facilitated** retro drafting on top of the retro that now exists), not core project management.

Order rationale: schema-risk first (2–3 define the work graph's core tables), daily-use surfaces before periphery, connectors before AI, and both last because they bind to stable issue semantics and a rich work graph. `design-system` was inserted after workspace-auth (design pass before the first product screens). Within 11–13: `notifications` owns the write seam and the mailer both others depend on; `mentions` then uses that seam — planned as a new `kind` and nothing else, until the maintainer's answer on auto-subscribe added a durable `issue_subscription` table and migration `0014_mentions` (so `search` takes `0015`); `search` is last because its plaintext walker extends the mention-aware one `mentions` already shipped in `packages/schema/src/rich-text/`, and its central risk (write amplification, and zero-cache replicating past a large GIN index) cannot be measured until it exists.

## Known gaps

Tracked so they are not forgotten. Neither is scheduled; both are promises made in prose that the code does not yet keep.

- **One-command export.** README ("Your data. One-command export, no lock-in") and VISION #5 both promise it; nothing implements it. TECHSTACK's self-host section makes the adjacent commitment (`yapm backup` → pg_dump + attachments tarball, "documented from day one") — also unimplemented. These are one change, and "free means free" leans on them: export is what makes the no-lock-in claim verifiable rather than rhetorical.
- **Attachments.** TECHSTACK specifies a local filesystem volume with optional S3; no upload path exists. Not in the locked v1 scope, listed here because the export gap above is scoped smaller without it.

## Differentiation commitments

- **Issue list shows reality, not just intention** — rows carry a delivery signal (PR/CI/review) and a divergence flag derived from the work graph; see [DESIGN.md](DESIGN.md). Layout built in `issue-core`; git data populates via `connectors`.
- **Connectors, not special-cases** — GitHub is the first implementation of a reusable first-party framework; GitLab and others follow as connectors.
- **AI as a moat is AI-over-the-work-graph** — BYO-key, self-hosted, provider-agnostic, operating under the same permission model as humans (which is also the safety story). Architected from the start, shipped once the graph is rich.

## Post-v1 (from VISION.md phasing)

- **Phase 2 — Delivery truth**: CI/deploy ingestion, automatic status transitions, DORA + review-health + CI-health views (team-level only). Lights up the issue-list reality strip's full signal.
- **Phase 3 — Incidents + cloud**: incident tracking (change failure rate, MTTR), managed cloud offering.
- Backlog of deliberate deferrals: full multi-color theme editor, "blocked-on" issue axis, estimates, sub-issues, additional connectors (GitLab, Jira/Linear import), true third-party plugin runtime, mobile/desktop apps, i18n, public API expansion, Yjs collaborative descriptions.
