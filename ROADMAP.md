# yapm — Roadmap

Scope decisions from the v1 scoping session (2026-07-23). Each item becomes an OpenSpec change (`openspec/changes/`) when its turn comes — proposals are written just-in-time, not upfront.

## V1 scope (locked)

**Shape**: one workspace per instance → teams → issues. Roles: admin / member / viewer (viewer free and unlimited).
**Tracking**: issues (status, priority, labels, assignee, TipTap description, comments) · cycles with auto-rollover · triage inbox · lightweight projects (name, lead, target date, membership, computed progress).
**Surfaces**: keyboard-first list · board · roadmap (timeline of projects) · command palette · search/filtering.
**Wedge proof**: GitHub App — branch/PR ↔ issue linking, PR state drives issue status **for teams that opt in** (off by default; the divergence flag is what happens otherwise), PR + checks visible on the issue.

**Opinionated defaults (not asked, decided per philosophy):** fixed status categories (Backlog / Todo / In Progress / In Review / Done / Canceled); estimates deferred; sub-issues deferred; notifications = in-app inbox + email for mentions/assignments.

With `retro-ai-draft` (18) the first AI *feature* on the change-9 substrate is in, and it lands where the stakes are highest: a model drafts wins, losses and improvements into a retro that sits beside a board of anonymous cards — reading none of them, no comment, and no identity column anywhere, generated lazily at the reveal so there is nothing to anchor on and nothing to spend on a retro nobody runs, off per team until an admin says otherwise, and labelled as unratified. With `retro-ratification` (19) that label finally has something behind it: each member's agree/disagree is synced to nobody but themselves — not to a teammate, not to a workspace admin — the verdict and counts are computed ONCE, server-side, at the `vote → discuss` advance so no counter exists for concurrent reactions to contend on, a single disagreement makes a proposal contested under a rule with no knob to turn, and an agreed improvement is one keystroke to the shipped conversion path — which forwards a null assignee, because a suggested owner would be the first per-person output in the entire AI layer. With `pm-digest-boundary` (20) the first yapm output to cross a permission boundary shipped *with* its boundary — a separate synced row rather than a widened read, four independent switches all defaulting off, evidence baked as plain text a reader outside the team could not open anyway, and a server-only audit table excluded from the sync schema entirely — and with `pm-digest-areas` (21) it acquired something to say, converting file paths into product areas under the GitHub permission already granted, without yapm ever reading a diff. With `pm-digest-governance` (23) the AI-features family closes, and the two words change 20's mission forbade become true rather than aspirational: the disclosure log is **retention-bounded** by a nightly sweep on the pg-boss instance that already exists (365 days, configurable, and running whether or not AI is enabled — a bound that lapses when the feature is switched off is not a bound), it is **auditable** through an admin-only view that reports what was disclosed and to how many readers and structurally cannot report a read, and a named reader can be told a digest is ready by an optional email carrying **a link and nothing else** — because a mailed artifact sits outside the kill switch, outside retention and outside the audit log simultaneously, which makes link-only a stated decision rather than a property somebody happened to preserve. It cost no migration and no container. What none of it undoes is stated in change 20's own words and left in them: retraction stops further reads, it does not un-read. With `deployment-hardening` (25) the part none of the above was any use without is finally true: the documented quickstart reads the operator's own `.env` instead of silently applying the secrets this repository publishes, a production boot on one of those secrets is a refusal that names it rather than a warning nobody reads, a published image resolves the browser's sync origin at runtime so it can sync on a host other than the one it was built for, images publish on every push to `main` whether or not release automation succeeded, and the upgrade path — with its forward-only, restore-from-backup rollback — is written down for both deployment shapes. None of it is a feature; all of it is the difference between a product that demos and a product that can be run.

Order rationale: schema-risk first (2–3 define the work graph's core tables), daily-use surfaces before periphery, connectors before AI, and both last because they bind to stable issue semantics and a rich work graph. `design-system` was inserted after workspace-auth (design pass before the first product screens). Within 11–13: `notifications` owns the write seam and the mailer both others depend on; `mentions` then uses that seam — planned as a new `kind` and nothing else, until the maintainer's answer on auto-subscribe added a durable `issue_subscription` table and migration `0014_mentions` (so `search` takes `0015`); `search` is last because its plaintext walker extends the mention-aware one `mentions` already shipped in `packages/schema/src/rich-text/`, and its central risk (write amplification, and zero-cache replicating past a large GIN index) cannot be measured until it exists. Both resolved when it did: the H10 answer removed write amplification entirely by moving index maintenance off the write path, and zero-cache was verified to replicate cleanly past `search_document` and its GIN expression index from empty volumes, with no publication change.

## Known gaps

Tracked so they are not forgotten — promises made in prose that the code does not yet keep.

- **One-command export. STILL OPEN.** README ("Your data. One-command export, no lock-in") and VISION #5 both promise it; nothing implements it. TECHSTACK's self-host section makes the adjacent commitment (`yapm backup` → pg_dump + attachments tarball, "documented from day one") — also unimplemented. These are one change, and "free means free" leans on them: export is what makes the no-lock-in claim verifiable rather than rhetorical. Half its substrate now exists: `attachments` (15) wrote the backup contract down and shipped it as a documented manual procedure — what a complete backup contains per provider, the database-then-files capture order (which the restore repeats, for the same reason in the other direction), and the `attachment` table as the manifest an S3 operator verifies their own bucket backup against (see [Backup and restore](apps/docs/src/content/docs/self-hosting/backup-restore.md)). **Change 16 (`editor-markdown`) shipped and does not close this either.** It built and proved the rich-text→markdown serialiser an export needs, and deliberately built no export surface: no `/api/v1/**/export.md`, no `yapm backup`, no zip, no bulk, no CLI, no server-side markdown rendering. One constraint it *did* settle for whoever picks this up — the serialiser lives in `packages/ui`, so an export that runs on the server cannot import it as it stands; that is a real cost of keeping the TipTap graph out of `apps/server`, and it is the right trade. **Change 17 (`editor-rich-content`) added serialiser cases for tables, images and fenced code and closes none of it either** — for the same reason, and with the same constraint: it also lives in `packages/ui`, and an image's markdown path is computed by the caller, so an export running anywhere else has to supply one. What is left for the change itself is the command that automates them. **Still unscheduled.**
- ~~**Attachments.**~~ **Closed** by changes 15–17 (see [SCOPE-editor-attachments.md](openspec/SCOPE-editor-attachments.md)): storage seam and routes, markdown interchange, then the editor nodes and the Files section. What deliberately stayed out: signed or shareable links of any kind, avatars, a `fileAttachment` document node, and a block editor.

## Differentiation commitments

- **Issue list shows reality, not just intention** — rows carry a delivery signal (PR/CI/review) and a divergence flag derived from the work graph; see [DESIGN.md](DESIGN.md). Layout built in `issue-core`; git data populates via `connectors`; and with `auto-status` a team can opt in to having the reality *correct* the intention instead of only flagging it.
- **Connectors, not special-cases** — GitHub is the first implementation of a reusable first-party framework; GitLab and others follow as connectors.
- **AI as a moat is AI-over-the-work-graph** — BYO-key, self-hosted, provider-agnostic, operating under the same permission model as humans (which is also the safety story). Architected from the start, shipped once the graph is rich.
